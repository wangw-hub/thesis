# 第5章 链上状态驱动的可信授权执行机制

## 5.1 问题定义

研究内容一将非连续时间策略规范化为唯一语义表示 I*。本章进一步解决多实例授权
环境中的状态一致性问题：授权方和验证方不仅需要判断时间策略，还必须确认能力令牌
对应同一条链、同一合约实例、同一资源状态和同一用户密钥版本，并在多个验证实例间
一致地拒绝重放。

## 5.2 系统实体与信任边界

系统包含 ADMIN、OWNER、AUTHORIZER、REVOCATION 和 AUDITOR 五类业务角色，
Issuer、两个独立 Verifier、PostgreSQL 共享 Nonce 后端，以及由四个 Validator 和
一个非验证 RPC 节点构成的 Besu QBFT 网络。BOOTSTRAP_FUNDER 仅承担实验链初始
注资，不拥有业务角色。系统不假设单个 RPC 或数据库故障时继续授权；依赖不可用时
采用 Fail-Closed。

## 5.3 授权状态模型

AuthorizationState 分别保存资源状态和用户状态。资源记录包含 owner、
policyDigest、epoch、status、policyVersion、stateVersion 和 updatedAtBlock；
用户记录包含 account、userKeyId、status、userVersion 和 updatedAtBlock。
策略更新、Epoch 推进和资源状态变化均推动单调版本；密钥轮换和用户状态变化推动
userVersion。REVOKED 为终态，不能恢复为 ACTIVE。

## 5.4 CAP2结构与完整绑定

CAP2 对规范化字节序列使用 Ed25519 签名。其公共字段包含 issuer、resourceId、
policyDigest、epoch、userKeyId、operation、notBefore、expiresAt、nonce 和
issuedAt，并进一步绑定 chainId、contractAddress、resourceStateVersion 和
userVersion。policyDigest 的输入是 I*，C(P) 仅在相应执行方法中作为可选派生
结构出现，不参与语义身份定义。

## 5.5 签发和验证流程

Issuer 首先在同一确认区块读取资源与用户状态，依次检查活动状态、用户密钥、
策略摘要和时间窗口；签名前再次读取状态，只有两次快照一致才生成 CAP2。Verifier
先检查规范编码和签名，再读取当前链状态，并按资源、用户、策略、Epoch、链上下文、
状态版本、用户版本、用户密钥、操作和时间边界的固定顺序验证，最后原子消费 Nonce。
RPC 失败或必要状态缺失均返回系统状态不可用，而不是策略拒绝。

## 5.6 共享Nonce与多Verifier一致性

共享 Nonce 的唯一键为 chain_id、contract_address、resource_id、epoch 和 nonce。
Verifier 使用 `INSERT ... ON CONFLICT DO NOTHING RETURNING 1` 原子消费该键，因此
同一能力在多个进程间最多只有一个实例成功。数据库异常不会触发进程内回退。并发
50、100 和 500 请求的验收均只有一次成功。

## 5.7 合约角色与状态转换

OWNER 登记资源并维护策略，AUTHORIZER 推进 Epoch，REVOCATION 管理暂停与撤销，
ADMIN 管理初始角色和用户，AUDITOR 不具有业务写权限。真实链状态机测试覆盖合法
转换、越权拒绝、版本单调性、密钥轮换、重复公钥拒绝和撤销终态。部署账户、业务
角色和引导资金账户相互分离。

## 5.8 安全与故障闭合分析

chainId 与 contractAddress 防止能力被直接搬移到另一条链或另一合约实例；
policyDigest、epoch、stateVersion 和 userVersion 使策略、资源或用户密钥更新后的
旧能力失效；operation、有效期和签名防止字段替换；共享 Nonce 提供可审计的一次性
消费。单 Validator 停机时 QBFT 继续出块；RPC 中断时 Issuer 停止签发；数据库
中断时 Verifier 拒绝授权；恢复后已消费 Nonce 仍不可重放。这些结果是给定实现和
故障模型下的实验支持，不构成形式化密码安全证明。

## 5.9 多主机实验环境

正式授权实验链采用 Besu 26.5.0、Java 21、chainId 2026072901、四个 QBFT
Validator 和一个非验证 RPC 节点。Genesis SHA-256 为
`7d431f01aab7d0c55c58c09346ee1f9a43475322a4aca304cfbb172b9b32add4`。
AuthorizationState 地址为
`0x9ef44cf538d0df457ba77c556d8785e48bfc436d`。PostgreSQL 16.14 为两个
Verifier 提供共享 Nonce。旧的基础设施验证链被冷保留，不进入本章正式数据。

## 5.10 V13正式实验设计

第一次正式运行因链读取、局部性、缓存命中、吞吐量和统计单位等协议偏差被判定为
失效，原始数据保留但不用于性能结论。V13 在提交
`8a3d795e22e5d9373c3053245e3b4040cd062dd5` 重新预注册，并冻结 B0、B1、C0、
C1 四种方法、三种碎片率、三种局部性、三种并发度和三个随机种子。

V13 包含 108 个因素配置、324 个含 seed 配置、9,720 个运行块、77,760 条请求和
233,280 条链读取记录。每个请求执行三次真实链读取：Issuer 初读、签名前复读和
Verifier 读。主要推断单位是运行块，方法比较按相同工作负载、seed 和 repetition
自然配对，并进行 10,000 次运行级 Bootstrap。请求级记录仅用于运行内部描述和
完整性审计。

## 5.11 V13正式实验结果

B0、B1、C0 和 C1 的运行级端到端中位数分别为 196.128、196.583、198.682 和
198.939 ms。配对中位差 B1-B0、C1-C0、C0-B0 和 C1-B1 分别为 +0.390、
+0.176、+0.257 和 +0.408 ms。四组均值差的 95% Bootstrap 置信区间跨越 0，
且改善与退化运行比例接近，因而不能据此声称稳定性能提升。

链读取占端到端时延的 98.66%-98.80%，局部匹配仅占约 0.017%-0.047%。并发度从
1 增至 4 和 16 时，中位延迟由约 52.8 ms 增至约 196-199 ms 和 340-349 ms，
是主要观测因素。碎片率增加会提高局部匹配耗时，但其绝对量级不足以改变由链读取
主导的端到端结果。

热点请求提高了缓存命中率，均匀请求命中率明显更低；然而命中率变化没有稳定转化为
端到端收益。四种方法的批次吞吐量中位数约为 17.78-17.93 请求/秒，不能支持方法
特有的吞吐优势。内存差异很小；CPU 字段为累计进程时间而非利用率，故不用于方法
CPU 效率结论。

## 5.12 C(P)消融和证伪

C(P) 与 I* 在 1,000 个随机合法和非法请求中没有非预期语义差异，说明其作为派生
执行结构能够保持 I* 语义。但 C0-B0 和 C1-B1 的配对差异没有稳定方向，C(P) 也
没有表现出 Baseline-I 难以复制的协议能力。因此本章正式冻结
`C(P)_DEMOTED_CONFIRMED_BY_VALID_RERUN`：C(P) 是可选派生 IR、消融与证伪
对象，不是研究内容二的核心性能贡献。

## 5.13 局限与讨论

实验规模为五个节点，不能外推至任意规模；链读取比例与当前逐请求读取边界、RPC
实现和网络环境相关；测试通过不等同于抵抗任意 Validator 合谋；系统不能阻止已获
授权用户分享能力或明文。缓存结论限于冻结容量、LRU 策略和负载矩阵。未来优化应
首先针对可验证的链状态读取边界，而不是夸大局部匹配的微小差异。

## 5.14 本章小结

本章在真实五节点 QBFT 环境中闭合了链上状态、CAP2、角色治理、共享 Nonce、多
Verifier 和 Fail-Closed 授权执行。正式重跑表明公共链读取主导时延，公平缓存和
C(P) 均未产生稳定工程收益。研究内容二的贡献因此收敛为可审计的链状态绑定与
多实例一致性控制，并以负面性能结果明确其方法边界。
