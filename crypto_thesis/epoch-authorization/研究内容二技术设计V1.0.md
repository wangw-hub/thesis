# 研究内容二技术设计V1.0

## 1. 研究问题与创新边界

研究问题为：如何使能力授权同时绑定具体资源、规范策略、当前Epoch、用户公钥、
操作、有效期和Nonce，从而使旧状态重放、跨用户替换和授权字段篡改被确定性
拒绝。该问题承接第四章的`I*`和`policyDigest`，并通过抽象已确认状态接口面向
后续联盟链，因而与“非连续时间约束”和“区块链数据共享”一致。

| 内容 | 定位 | 独立创新判断 |
|---|---|---|
| Ed25519、SHA-256 | 标准组件 | 否 |
| Nonce防重放 | 标准机制 | 否 |
| Epoch版本 | 常见状态机制 | 单独不足 |
| 用户公钥指纹 | 协议绑定字段 | 有限 |
| 资源—策略—Epoch—用户联合绑定 | 系统协议组合 | 组成贡献 |
| Baseline-I | 第四章主表示接口 | 强基线 |
| Proposed-C | 候选层次执行机制 | 待实验判断 |
| 联盟链审计 | 后续工程贡献 | 需真实链验证 |

本章候选贡献是具有明确状态不变量、规范令牌和公平可证伪对照的授权协议设计，
不是新密码算法。闭环为：

```text
研究问题 -> 攻击模型 -> Epoch状态机 -> CAP1
        -> Baseline-I / Proposed-C -> 本地原型
        -> 攻击测试 -> 公平对照 -> 保留或降级C(P)
```

## 2. 系统实体与信任关系

```mermaid
flowchart LR
    DO[数据拥有者 DO] -->|注册资源/策略管理| BC[确认状态接口 BC]
    DU[数据用户 DU] -->|公钥与授权请求| AS[授权服务 AS]
    AS -->|读取资源与用户状态| BC
    AS -->|加载 I* / C(P)| PR[策略仓库]
    AS -->|签发 CAP1| DU
    DU -->|CAP1 + 公钥证明| V[验证方]
    V -->|状态与Nonce检查| BC
    AU[审计者 AU] -->|只读查询| BC
```

| 实体 | 持有数据与权限 | 信任边界 |
|---|---|---|
| DO | 资源、原始策略、注册与状态转换权限 | 不持有AS签名私钥 |
| DU | 用户标识、长期公私钥、CAP1 | 私钥不得上链 |
| AS | Ed25519签名私钥、Matcher、状态读取、签发逻辑 | 本阶段假定可信 |
| BC | 资源、用户、Epoch、摘要、状态 | 本地存储仅模拟已确认状态 |
| AU | 公开状态、拒绝码、审计事件 | 只读，不见秘密 |

公开数据包括资源标识、策略摘要、Epoch、状态和审计结果。AS私钥、DU私钥、
系统根秘密和明文资源不得上链。

## 3. 威胁模型与安全目标

攻击者A1至A6及边界见`docs/threat-model.md`。安全目标与依据如下：

| 目标 | 机制 | 依据 |
|---|---|---|
| G1授权完整性 | CAP1全字段签名 | Ed25519安全假设+实现测试 |
| G2用户绑定性 | `SHA-256(pkDU)=userKeyId` | 摘要假设+状态机逻辑 |
| G3状态新鲜性 | 令牌Epoch等于当前资源Epoch | 状态机逻辑 |
| G4时间有效性 | 半开有效期与当前策略双检查 | 验证逻辑 |
| G5重放抵抗 | 原子`consume_once` | Nonce状态逻辑 |
| G6策略一致性 | 当前摘要相等检查 | 状态逻辑 |
| G7操作绑定 | 签名操作字段与请求操作相等 | 签名+验证逻辑 |
| G8可审计拒绝 | 冻结验证顺序与拒绝码 | 实现与测试 |

系统不声称阻止合法用户共享私钥，也不把测试通过写成密码学证明。

## 4. Epoch状态机

资源状态为`ACTIVE/SUSPENDED/REVOKED`。`REGISTER`初始化状态；
`UPDATE_POLICY`、`ADVANCE_EPOCH`、`SUSPEND`、`ACTIVATE`和`REVOKE`均使
Epoch单调增加。`REVOKED`是终态。完整转换见`Epoch状态机规范.md`。

状态更新必须先确认，签发再读取新快照。Epoch是授权版本，不是墙上时间。

## 5. CAP1能力令牌

CAP1与NTP1独立版本管理。基础字段为版本、签发者、资源、策略摘要、Epoch、
用户公钥指纹、操作、`notBefore`、`expiresAt`、Nonce和签发时间。Proposed-C
扩展字段为`matched_node`和`cover_version`。规范编码见`CAP1格式规范.md`。

## 6. Baseline-I

```text
BASELINE-ISSUE(req):
  rs, us <- confirmed state
  reject unless both ACTIVE and SHA256(req.pk)=us.userKeyId
  P <- repository[rs.policyDigest]
  reject unless IntervalMatcher(P.I*, slot(req.now))
  expiry <- min(req.now+TTL, containing_interval.end)
  return SignCAP1(rs, us, req, expiry)

BASELINE-VERIFY(cap, context):
  verify signature -> current resource/user state -> policyDigest -> Epoch
  -> userKeyId -> operation -> time bounds -> IntervalMatcher
  -> atomic nonce consumption
```

匹配复杂度为 \(O(\log k)\)，其余本地字典状态读取和固定长度密码操作按原型
接口记为常数成本。正式联盟链读取延迟不在本阶段结论中。

## 7. Proposed-C

主方案选择“节点标识授权”。当前槽沿叶到根检查是否命中`C(P)`，命中节点及
Cover版本写入CAP1并签名；验证方重新计算节点绑定。该步骤真实消费`C(P)`，
而不是只生成后仍用区间判断。

```text
PROPOSED-ISSUE(req):
  执行与BASELINE-ISSUE相同的状态和用户检查
  node <- first ancestor(slot(req.now)) in C(P)
  reject if node absent
  expiry <- min(req.now+TTL, containing_interval.end)
  return SignCAP1(..., node, coverVersion)

PROPOSED-VERIFY(cap, context):
  执行与BASELINE-VERIFY相同的公共检查
  recomputed <- ancestor match over C(P)
  reject unless recomputed node/version equals signed extension
  atomic nonce consumption
```

祖先检查为 \(O(\log U)\)。相较Baseline-I，它增加Cover索引、48字节CAP1
扩展和节点重算；潜在收益仅来自后续节点级复用，当前原型尚未证明收益。
高碎片时`c`增大，该方案可能退化。

## 8. 公平比较与证伪

两方案只替换策略执行器，共享Issuer、Verifier、CAP1、Ed25519、Nonce、状态、
TTL、验证顺序和工作负载。冻结H-C1至H-C4和降级条件见
`docs/falsification-rules.md`。Baseline-I不得使用线性扫描或关闭缓存。

## 9. 原型与测试计划

本地原型采用线程安全内存状态与Nonce存储，只验证协议逻辑，不作为联盟链性能
数据。测试包括CAP1、签名、状态机、攻击矩阵、并发Nonce、Hypothesis往返及
两种Matcher语义一致性。验收门槛要求语义不一致、非法接受、合法误拒、并发
重复成功、不变量违反和编码错误均为0。
